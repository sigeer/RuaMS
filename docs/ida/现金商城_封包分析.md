## 2. 客户端结构

`CCashShop` 由 `CStage::OnSetCashShop`（`0x776A4F`）用 `ZAllocEx::Alloc(7948)` 分配，再由 `set_stage` 装成当前舞台。
所有字段以下文 **字节偏移** 为准，括号里是 IDA 的 `this[下标]`（下标 × 4）。

| 偏移 | 下标 | 语义 | 依据 |
|------|------|------|------|
| `+24` | `[6]` | 「请求在途」标志：发包前置 1，收到应答清 0 | `sub_46DADD` / `sub_46C036` 等 |
| `+36` / `+48` / `+60` | `[9]` / `[12]` / `[15]` | 点券 / 抵用券 / 信用卡的加密副本 | `OnQueryCashResult` 用 `_ZtlSecureFuse` 写入 |
| `+64` | `[16]` | 商城是否已打开（`LoadData` 的 `Decode1`） | `0x471F63` |
| `+80` | `[20]` | 1080 字节定长块起点（`LoadData` 的 `DecodeBuffer`），**终点正好是 `+1160` 的现金仓数组** | `0x47245D` |
| `+1160` | `[290]` | 现金仓条目数组（55 字节 / 条） | `OnCashItemResLoadLockerDone` |
| `+1164` | `[291]` | 仓库格数 | 同上 |
| `+1168` | `[292]` | 角色栏位数 | 同上 |
| `+1172` | `[293]` | 商城名（`LoadData` 的 `DecodeStr`） | `0x471F7F` |
| `+1180` | `[295]` | 愿望单 SN[10]（40 字节） | `OnCashItemResLoadWishDone` / `sub_479844` |

| `+1224` | `[306]` | 愿望更新时「不弹提示」标志 | `sub_479844` |

> 与 `sub_47B93C`、`sub_47B603`、`sub_479844` 里直接用的 `this+617` / `this+976` / `this+1391`（dword）自洽。

### 2.2 `CCashShop::LoadData`（`0x471F37`）——`SET_CASH_SHOP` 的正文解析

按 Decode 顺序：

```
v = Decode1();                 // → this+64（即 [16]），非 0 才继续读商城名
if (v) {
    name = DecodeStr();        // [293]（服务端写的是账号名 / NexonClubID）
    ... 从 WZ 读背景、按职业选背景图 ...
    ... 用 CS_COMMODITY 列表建分类表（910xxxxx / 800xxxxx 过滤 + CRand32 打乱特价）...
}
DecodeBuffer(this + 80, 0x438);      // ★ 1080 字节定长块
sub_472AAF(packet):  n = Decode2(); if (n) { 预分配 n; DecodeBuffer(this[18], 8*n); }    // 愿望 8 字节/条
sub_472AF6(packet):  n = Decode2(); if (n) { 预分配 n; DecodeBuffer(this[19], 104*n); }  // 商品行 104 字节/条
... 按分类把商品行挂到 tab 子列表，计数写进 28 字节步长的分类项 ...
sub_472B3B(packet):  n = Decode2(); if (n) { 预分配 n; DecodeBuffer(this[319], 68*n); }  // 现金仓行 68 字节/条
```

> ★ **这里有一处与当前服务端下发长度对不上的地方，见 §10 第 1 条。** 客户端在该处读 **固定 1080 字节**
> （`DecodeBuffer(this+80, 0x438)`；`this+80` 到 `+1160` 的现金仓数组之间正好 1080 字节），
> 而 `PacketCreator.openCashShop` 在该位置写的是变长数据：
> `4 + 2 + 9n（特价条目）+ 121 + 12M（8 tab × 2 组 × N 条三元组）= 127 + 9n + 12M`。
> 要凑满 1080 需要 `9n + 12M == 953`，但左边恒为 3 的倍数，**无解**。
> 说明两者描述的根本不是同一块内容，必须靠抓包定案（§10 第 1 条）。

### 2.3 `CCashShop::Init`（`0x468F3E`）

`Init` 只做界面重建，**不读封包**：清 `CWvsContext` 的 field UI、把 `+1180` 起的 40 字节愿望数组清零、
按职业选背景（`Unknown/1000==1` → `SP_1302` backgrnd1，`Unknown/100==21 || Unknown==2000` → `SP_5361` backgrnd2，
其余 `SP_1301` backgrnd）、`CreateLayer`、8 次 `CWnd::CreateWnd`（偏移 340 / 616 / 976 / 1344 / 1388 / 1876 / 1912 / 1948）、
`CInputSystem::ShowCursor`、`PlayBGM(SP_1249_..._SHOPBGM)`。

## 3. 进入 / 退出

### 3.1 进入：C→S `ENTER_CASHSHOP = 0x28`

客户端发出的是**空 payload**（只改 stage，不做别的）。服务端 `EnterCashShopHandler` 校验
`cannotEnterCashShop()` / 事件实例 / 迷你副本 / 已打开，然后：

```
SyncCharAsync(SyncCharacterTrigger.EnterCashShop)
closePlayerInteractions / closePartySearchInteractions / unregisterChairBuff / SaveBuff
EnterExtralWorld
CancelAllBuffs / cancelAllDebuffs / forfeitExpirableQuests
state = CashShopManager.GetState(client)          // 一次 RPC 取全部状态
Send openCashShop(client, mts: false)             // SET_CASH_SHOP
Send showCashInventory(accountId, state)          // 0x145 / 0x4B
Send showGifts(LoadPlayerGifts(client))           // 0x145 / 0x4D
Send showWishList(state.WishList, update: false)  // 0x145 / 0x4F
Send showCash(state.Cash)                         // 0x144
player.getCashShop().open(true)
```

顺序与客户端无关（各分支互不依赖），但 `openCashShop` 必须在最前，否则 `CCashShop` 还没被 `set_stage`。

### 3.2 `SET_CASH_SHOP = 0x7F` 布局（`PacketCreator.openCashShop(c, mts: false)`）

| 段 | 服务端写法 | 客户端读法 |
|----|-----------|-----------|
| 角色信息 | `addCharacterInfo` | `CharacterData::Decode`（在 `OnSetCashShop` 里，构造器之前） |
| 打开标志 | `writeByte(1)` | `Decode1` → `[16]` |
| 账号名 | `writeString(AccountName)` | `DecodeStr` → `[293]` |
| 定长块起 | `writeInt(0)`、`writeShort(特价条目数)`、每条约 9 字节 | — |
| 占位 | `skip(121)` | — |
| 畅销表 | 8 个 tab × 2 次 × 每个 SN：`int tab / int j / int sn` | — |
| 定长块止 | `writeInt(0)`、`writeShort(0)` | ★ 客户端在这里是 `DecodeBuffer(+80, 1080)`，见 §10 |
| 尾 1 | `writeByte(0)` | 构造器 `Decode1` → `[317]` |
| 尾 2 | `writeInt(75)` | 构造器 `Decode4` → `[318]`（买 MapleLife 的等级门槛，见 `sub_46DADD` 的 `[318] < 30`） |

### 3.3 退出：`CCashShop::SendTransferFieldPacket`（`0x47C108`）

```c
COutPacket::COutPacket(38);      // CHANGE_MAP，payload 为空
CClientSocket::SendPacket(...);
set_stage(new CInterStage());    // 回到过渡舞台
```

商城内部有 16 处调用它（结算失败、名字被占用、收到 162/163/164 等）。服务端
`ChangeMapHandler` 用 `p.available() == 0` 识别这条路：

```csharp
bool enteringMapFromCashShop = p.available() == 0;
if (enteringMapFromCashShop) { await c.LeaveCashShop(); return; }
```

`LeaveCashShop()` 清掉 `TradeServer`（会话状态记在 `IChannelClient.TradeServer` 上，
非空即表示在商城 / 拍卖行），**不同步任何角色数据**，只发
`PlayerPreEnterChannelCommand`；账号切服状态由该命令在发 `CHANGE_CHANNEL` 之前设置。
重连时 `LoginService.PlayerLogin` 重新取中心服那份 —— **商城期间改过的背包 / 现金仓 / 余额
一律以中心服为准**，频道那份旧镜像不上传。

## 4. C→S `CASHSHOP_OPERATION = 0xE5`

第一个字节是子操作码。以下字段序全部来自逐函数反编译（不是从 `push` 立即数推的）。

| op | 含义 | 构造点 | 精确字段序 |
|----|------|--------|-----------|
| `0x03` | 购买单品 | `sub_46DADD` | `1(3)` `1(mask==2)` `4 cashMask` `4 sn` `4 freeTestFlag` |
| `0x1E` | 购买礼包 | `CCashShop::OnBuyPackage` `0x46E121` | `1(30)` `1(mask==2)` `4 cashMask` `4 sn`（`itemId/10000==910`） |
| `0x04` | 赠送 | `CCashShop::SendGiftsPacket` `0x46F940` | `1(4)` `4 [326]` `4 [327]` `str 收礼人` `str 留言` |
| `0x05` | 愿望单（新增） | `CCashShop::OnSetWish` `0x470D7D` | `1(5)` + `4 sn` × 10（新 SN 填第一个空位） |
| `0x05` | 愿望单（删除） | `CCashShop::OnRemoveWish` `0x470EDD` | `1(5)` + `buffer 40`（整份 10 个 SN） |
| `0x06` | 背包扩容 | `sub_46C036` | `1(6)` `1(mask==2)` `4 cashMask` `1 0` `1 invType` |
| `0x07` | 仓库扩容 | `sub_46C55B` | `1(7)` `1(mask==2)` `4 cashMask` `1 0` |
| `0x08` | 角色栏扩容 | `sub_46C6F8` | `1(8)` `1(mask==2)` `4 cashMask` `4 sn` |
| `0x09` | SD 抵用金购买 | `sub_46C8E1` | `1(9)` `1(mask==2)` `4 sn`（`SP_5208`：额外延长 `D` 天） |
| `0x0D` | 现金仓 → 背包 | `sub_472632` | `1(13)` `buffer 8 cashId` `1 invType` `2 slot` |
| `0x0E` | 背包 → 现金仓 | `sub_472820` | `1(14)` `buffer 8 cashId` `1 invType` |
| `0x1A` | 销毁现金装备退抵用券 | `sub_46BDE1` | `1(26)` `4 生日码` `buffer 8 cashId`（仅限无期限的现金装备；退额 = `售价 × (100-剩余%) / 100`） |
| `0x1D` | 情侣戒指 | `sub_46FFE7` | `1(29)` `4 生日` `4 cashMask` `4 sn` `str 收礼人` `str 文字` |
| `0x1F` | 赠送礼包 | `CCashShop::OnGiftPackage` `0x46FC3B` | `1(31)` `4 生日` `4 sn` `str 收礼人` `str 留言` |
| `0x20` | 金币买任务道具 | `sub_46E5C5` | `1(32)` `4 sn`（itemId 必须在 `[80000000, 90000000)`） |
| `0x21` | 刷新畅销榜 | `sub_473149` | `1(33)`（无后续字段） |
| `0x23` | 友谊戒指 | `sub_470A5A` | `1(35)` `4 生日` `4 cashMask` `4 sn` `str 收礼人` `str 文字` |
| `0x28` | 未知（翻页？） | `sub_46BD0E` | `1(40)` `4 int` |
| `0x2E` | 改名 | `sub_47342F` | `1(46)` `4 sn` `str 旧名` `str 新名` |
| `0x31` | 转区 | `sub_473601` | `1(49)` `4` `4` |
| `0x06` / `0x07` | 时长券扩容 | `sub_470653` | `1((itemId/1000==9110)+6)` `1(mask==2)` `4 cashMask` `1 1` `4 sn` |

几点说明：

1. **`cashMask` 是位图**：1 = 点券（NX Credit），2 = 抵用券（MaplePoint），4 = 信用卡（NX Prepaid）。
   服务端 `CashShopServer.GetCash(state.Cash, cashType)` 直接用它取余额。
   第二个字节 `mask==2` 是「只够抵用券」的提示位，客户端发上来但服务端不用。
2. **`0x03` 的第 5 个 int** 是「免费试用」标志（`SP_490_YOU_MAY_TEST_THIS_ITEM_FOR_FREE...` 点了「是」）。
3. `sub_470653` 同时服务 `0x06`（时长券，`itemId/1000==9110`）和 `0x07`（`itemId/1000==5430`），
   操作码按 `(itemId/1000==9110)+6` 动态算，所以**同一个函数会发 6 或 7**。
4. **`push 0E5h` 的假阳性**：`CCSWnd_Locker::OnCreate`（`0x4AFEBB`，`0x4AFFD6`）和 `CCSWnd_Locker::Draw`
   里也有 `push 0E5h`，那是 `CWnd::CreateWnd(..., 0x3E9, 1, 0xE5, 0x1D, 0x43, 0)` 的**控件 id**，
   不是封包操作码。

### 4.1 服务端分支覆盖

`CashOperationHandler` 目前处理 `0x03 / 0x1E / 0x04 / 0x05 / 0x06 / 0x07 / 0x08 / 0x0D / 0x0E / 0x1D / 0x20 / 0x23 / 0x2E / 0x31`。

**客户端会发、服务端没有分支**：`0x09`（SD 抵用金购买）、`0x1A`（销毁现金装备退抵用券）、
`0x1F`（赠送礼包）、`0x21`（刷新畅销榜）、`0x28`。落到 `else` 只打一条 warning，不回包
（客户端该请求的 `[6]` 会一直挂着，之后所有操作都会被客户端的 `[6] != 0` 挡掉）。

### 4.2 `0x03` / `0x1E` 的客户端前置校验（供服务端对照）

`sub_46DADD` 在发包前依次检查：商城已打开（否则 `NoticeFailReason(195)`）、没有在途请求、商品在售、
`mask` 至少有一位余额够、`Data == 1802019`（鲁道夫宠物）要额外确认、试用券确认、`IsUsableItem`、
「你已经有了」确认、等级门槛（`[318] < 30` 时禁止 MapleLife）、角色栏位（`>= 15` 或空的栏位为 0 时拒绝）。
服务端把**扣费与落仓**都放到中心服之后，这些前置只影响提示，不影响安全性。

### 4.3 `0x0D` / `0x0E` 的客户端前置

- `0x0D`（`sub_472632`）：要求客户端背包里目标页**该格为空**、现金仓里能找到这个 cashId、
  且 `sub_4729B5` 判定不冲突（`SP_2965_THIS_ITEM_CANNOT_BE_TRANSFERED_...`）。
- `0x0E`（`sub_472820`）：`FindCashItemSlotPosition` 先在背包里定位，
  再 `sub_5D31C5` 判断能否移动（否则 `SP_2507_THIS_ITEM_CANNOT_BE_MOVED`）。

### 4.4 `COUPON_CODE = 0xE6`（`CCashShop::OnStatusCoupon` `0x4710E8`）

客户端发：`str code` `str second`〔`str third`，仅当非空〕，**没有前置的 2 字节**；
要求 `[16]`（商城已打开）且 `[6] == 0`。

服务端 `CouponCodeHandler` 目前是：

```csharp
p.skip(2);
string code = p.readString();
```

⚠️ **与服务端不一致**：多跳了 2 字节，会把这个字符串的前 2 字节吃掉（或直接读越界）。
该类本身已标 `[Obsolete]`，本次未改动，记录在此以免被误认为已核对。

## 5. S→C `QUERY_CASH_RESULT = 0x144`

`PacketCreator.showCash(nxCredit, maplePoint, nxPrepaid)` → 三个 int。

客户端 `CCashShop::OnQueryCashResult`（`0x478F81`）：

```c
v1 = Decode4(); v2 = Decode4(); v3 = Decode4();
if (v1 < 0 || v2 < 0 || v3 < 0) {          // 负值 = 出错
    NoticeFailReason(164);                  // SP_557 未知错误
    SendTransferFieldPacket();              // 把玩家送出商城
} else {
    [28] = TSecType::Tear(v1);              // 三份加密副本
    [40] = TSecType::Tear(v2);
    [52] = TSecType::Tear(v3);
    InvalidateRect(+7648);                  // 余额显示
    [6] = 0;                                // 清「请求在途」
    if ([310]) SendBuyAvatarPacket();
    if ([322]) SendGiftsPacket();
    if ([305] && FindWishList([305]) >= 0) { OnRemoveWish([305]); [305] = 0; }
    if ([312]) { [312] = 0; GiftWishItem(); }
}
```

这三个 int 是**唯一的余额来源**，客户端在收到它之前不会去别处取数，
所以商城每次操作完成后都必须补发一次（哪怕余额没变），否则客户端 `[6]` 会一直挂着。

**这是商城唯一的余额刷新闻封**：

- C→S `CHECK_CASH (0xE4)`（`sub_472958`，空 payload，要求 `[6]==0` 并置 `[6]=1`）→ `TouchingCashShopHandler`
  → `CashShopManager.EnableActions` → `showCash`。
- 商城里每次操作完成后服务端都会补发一次 `showCash`（`CashShopManager.SendCash`）。
- 拍卖行**不用这个包**，它读 `MTS_OPERATION2 (0x15B)` 两个 int（`MTSPacketCreator.ShowMTSCash`）。

**`0x4B` 现金仓（`OnCashItemResLoadLockerDone`）**

即 `short n + 55×n + short + short`，与 `PacketCreator.showCashInventory` 一致。

（`addCashItemInformation(..., giftMessage)` 的礼物分支正好 98 字节，见 §7）。

**`0x4F` / `0x55` 愿望单**：都是**固定 40 字节**（10 个 int），与 `showWishList` 的
10×`writeInt`（不足补 0）一致。注意 `0x4F` 是「读城时下发」，`0x55` 是「更新后的回显」，

## 10. 客户端已验证 / 仍未确认

**客户端已验证（逐函数反编译）**

- `CStage::OnPacket` 只认 `0x7D / 0x7E / 0x7F`，商城由 `OnSetCashShop` 构造 `CCashShop`（7948 字节）；

- `0xE5` 全部构造点的精确字段序（§4），包括 `0x2E` / `0x31` / `0x1F` / `0x28` 这些服务端还没处理的；
- `sub_470653` 会按 `itemId/1000` 动态发 `0x06` 或 `0x07`；
- `0x144` 的「任一 int 为负 → `NoticeFailReason(164)` + 踢出」；

- `LoadData` 的四段数组读取（1080 / 8n / 104n / 68n）；
- 退出走 `CHANGE_MAP(38)` 空包（`SendTransferFieldPacket`，16 处调用）。

**仍未确认**

1. **`LoadData` 里那 1080 字节（`DecodeBuffer(this+80, 0x438)`）的来源与内容。**
   `this+80` 到 `this+1160`（现金仓数组）之间正好 1080 字节，说明客户端把这一整块当成一个定长表读。
   而服务端 `openCashShop` 在该位置写的是 `int 0 + short n + 9n 特价 + skip(121) + 12M 畅销三元组`
   = `127 + 9n + 12M` 字节；要凑满 1080 需要 `9n + 12M == 953`，左边恒为 3 的倍数，**无解**。
   所以这段要么是客户端从 `CS_COMMODITY` / WZ 自己填的（封包里那部分其实是另一段变长数据），
   要么布局与本文理解不同。**必须靠真实抓包逐字节对齐后才能定论**；
   在此之前不要把这段当成「已经对过」。
   连带影响：构造器在 `LoadData` 之后紧接着 `Decode1` → `[317]`、`Decode4` → `[318]`
   （即服务端尾部的 `writeByte(0)` / `writeInt(75)`）；如果上面那 1080 字节真的读不齐，
   这两个字段的位置也会跟着错位。这条是本次唯一一处「疑似真实缺陷、但客户端证据不足以下结论」的地方，
   故意不动代码。
2. **`0x28`（`sub_46BD0E`，`1(40)` + `4`）的语义**：它在 `CCSWnd_List::ChangePage` 路径里被构造，
   服务端没有分支，也没有对应的 S→C 应答。
3. **`0x4B` 之后客户端是否期待 `0x71`（限购数量变化）**：`OnCashItemResLimitGoodsCountChanged`
   只接受 `4 commodityId + 4 sn + 4 count`，服务端不发，功能上也不缺（客户端会自己按 `IsUsableItem` 判断）。
4. **`0x146` / `0x149` / `0x14B` / `0x14C`** 只核对了字段序与文案，服务端都不下发；
   其中 `0x14B`（转区）在本仓库已经因为「移除了大区概念」被显式拒绝（`CashOperationHandler` 的 `0x31` 抛
   `BusinessNotsupportException`）。
5. **`LoadData` 里愿望数组是 8 字节/条（`8n`）而运行时愿望数组是 40 字节（10 个 int）** ——
   两者尺寸不同，说明它们不是同一个结构（前者是「收藏/浏览记录」之类，后者才是愿望单）。

### 11.1 为什么「退出不保存」

商城期间频道侧的 `Player` 仍在世界里，背包也还能被别的路径改（拾取、脚本等），
所以频道这份现金仓/余额天然是过期的。若退出时把它写回中心服，就是以旧盖新。

因此退出时**连同步都不做**：`LeaveCashShop` 只清 `TradeServer` 并发
`PlayerPreEnterChannelCommand`，账号切服状态在该命令里设置；客户端重连后
`LoginService.PlayerLogin` 直接返回中心服那份 `PlayerGetterProto`。
原来的 `SyncCharacterTrigger.LeaveCashShop` / `LeaveMts` 在中心服本来就命中
`keepMasterState` 分支（`origin.Character` 不赋值、`MergeAccountGame` 跳过），
整个 `PlayerSaveProto` 传过去后被整份丢弃，只剩设置状态位这一个副作用 ——
现在状态位由命令设置，这两个 trigger 已删除（枚举 4 / 6 留空）。

在商城里**直接断线**时没有重连流程可依赖，仍走 `LogoffCashShop` / `LogoffMts`
（`Character.logOff` 按 `TradeServer` 的类型选择），由 `CharacterManager.Update`
保留中心服那份数据并置账号为 `LOGIN_NOTLOGGEDIN`。

### 11.2 为什么购买时不生成物品

`SET_CASH_SHOP` 的现金条目只有 55 字节（§7），客户端要的全部信息都在里面。
中心服没有 WZ 模板（多进程模式下它拿不到 `Item.wz`），也没有必要为了显示生成真物品。
所以 `BuyCashItem` 只把「买的是哪一件」——`CashItemPlaceholderProto { sn, itemId, quantity, expiration, cashId }`
——送到中心服，由它造一条 `ItemProto` 落进现金仓；
真物品等玩家回到主世界、走 `CashItem2Item` 时才按 SN 生成。
`expiration` 必须由频道算好带过去（中心服没有模板），否则玩家在商城待久了有效期会被重新起算。

## 12. 与旧实现的差异（逐条）

| 项目 | 旧实现 | 客户端实测 | 结论 |
|------|--------|-----------|------|
| 余额的存放 | 频道侧 `CashShop` 持有三个 int，退出时写回 | 客户端不关心谁持有，只认 `0x144` | ❌ 会被旧数据覆盖，已改为中心服权威 |
| `CASHSHOP_OPERATION` 的收尾 | 部分包尾补过字节 | **0x145 没有收尾字节**（§6.1） | ❌ 多写的字节会被下一条包当子操作码读掉 |
| `showWishList` 长度 | 按实际条数写 | 固定 **40 字节**（10 个 int，缺位补 0） | ✅ 现实现正确 |
| `showBoughtCashPackage` 第 2 段 | 写 `short 0` | `short 抵用券`，`>0` 时换文案 | ⚠️ 形状对，但永远不提示礼包自带抵用券 |
| `showCouponRedeemedItems` 第 2 段 | 写 `int items.Count` + 8 字节/条 | 相同（`4 m` + `8×m`） | ✅ |
| `showBoughtQuestItem` | `int 1 + short 1 + byte 0x0B + byte 0 + int itemId` | `int n + 8×n`，n 恒为 1 时形状一致 | ✅ |
| `0x0E` 的页校验 | 信任客户端给的 invType | 客户端给的是背包页，中心服按 cashId 自己找 | ✅ 已有范围校验 1..5 |
| `0x04` 赠送 | 频道侧直接落库 | 客户端先收 `0x147` 再发 `0x04` | ✅ 通道一致，落库改由中心服 `GiftManager` |
| `0x06` / `0x07` 价格 | 频道侧算并扣 | 客户端只送 `cashMask` + 页/SN，价格来自模板 | ✅ 价格必须由频道给，扣费必须在中心服 |
| `COUPON_CODE 0xE6` | `p.skip(2)` | 客户端直接 `EncodeStr` ×2（可有第 3 个） | ❌ 多跳 2 字节（已标 `[Obsolete]`，本次未改） |
| `0x09` / `0x1A` / `0x1F` / `0x21` / `0x28` | 无分支 | 客户端都会构造 | ⚠️ 只记 warning，不回包（`[6]` 会挂着） |
